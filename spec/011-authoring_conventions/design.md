For a reader arriving at the finished docs, nothing about the entry path changes —

## 1. The Banner (D2)

### Grammar

Placed as the first non-blank line after the H1, separated by one blank line:

```markdown
# RabbitMQ Subscription Configuration

> **Reference** · Applies to **Brighter V10** · Prerequisites: [Basic Configuration](/contents/BrighterBasicConfiguration.md)
```

Formal shape, and the pattern `pagelint.py` enforces:

```python
BANNER_RE = re.compile(
    r'^> \*\*(Tutorial|How-to|Reference|Explanation)\*\*'      # page type
    r' · Applies to \*\*(' + '|'.join(APPLIES_TO) + r')\*\*'   # see note below
    r'( · Prerequisites: .+)?$'                                 # optional
)
```

- Separator is **` · `** — space, U+00B7 MIDDLE DOT, space. One character, chosen
  because it is visually light and does not occur in our heading or link text.
- **Page type** is one of four. `Reference` doubles as the catch-all for pages outside
  Diátaxis (`FAQ.md`, `Glossary.md`, `V10MigrationGuide.md`) — material you consult
  rather than read through. Requirements § The Conventions records why a fifth value
  was rejected.
- **Prerequisites** is omitted entirely when there are none. Never
  `Prerequisites: none`.

> **Corrected 2026-08-04.** This section originally fixed the vocabulary as
> `Brighter V10 | Darker V10 | Brighter and Darker V10`, on the assumption that Darker
> tracks Brighter's version. **It does not.** Darker's latest release is **4.1.1** and
> its tags (4.1.1, 4.1.0, 4.0.1, 4.0.0, 3.0.0, 2.0.79) show an independent line, so
> "Darker V10" is a version that has never existed. The banner sweep put that claim on
> 10 pages, including `Glossary.md` and `ShowMeTheCode.md`, before it was caught.
>
> The vocabulary is now `APPLIES_TO = ('Brighter V10 and Darker V4', 'Brighter V10',
> 'Darker V4')`, defined once in `tools/pagelint.py` and imported by
> `apply_banners.py`, with `CLAUDE.md` documenting it. Darker's next release is in
> flight and its source is ahead of what is deployed; the version segment gets bumped
> when it lands, which is one edit to `APPLIES_TO`, one to `pagetypes.tsv`, and a
> re-run.

### Worked examples

| Page | Banner |
|---|---|
| `TutorialFirstCommand.md` (Spec 009) | `> **Tutorial** · Applies to **Brighter V10**` |
| `RabbitMQConfiguration.md` | `> **Reference** · Applies to **Brighter V10** · Prerequisites: [Basic Configuration](/contents/BrighterBasicConfiguration.md)` |
| `ReactorAndProactor.md` | `> **Explanation** · Applies to **Brighter V10**` |
| `CQRSWithBrighterAndDarker.md` | `> **Explanation** · Applies to **Brighter and Darker V10**` |
| `FAQ.md` | `> **Reference** · Applies to **Brighter V10**` |

### Assigning a page type to 105 pages

Automation proposes; a human decides. The proposal comes from signals we already have:

1. **`SUMMARY.md` section** — pages under *Transports*, *Outbox and Inbox* and
   *Scheduler* skew Reference; *Event Driven Architectures* skews Explanation.
2. **Title verb** — a gerund or imperative (`Implementing`, `Using`, `Building`,
   `Migrating`) indicates How-to.
3. **Mode score** from `modemix.py` — a page scoring one mode takes that mode.
4. **Everything else** lands in a review queue rather than a default. A wrong page type
   is worse than a slow one: it tells the reader the page is something it is not.

Output: `spec/011-authoring_conventions/pagetypes.tsv`, one row per page —
`path` · `proposed type` · `confidence` · `signal that fired` · `human verdict`. The
sweep script reads the **verdict** column, never the proposal, so the file has to be
reviewed before the banner can be applied. That is deliberate friction.

**A blank verdict is a hard stop, not a fallback.** If any row lacks a verdict, the
sweep script prints the offending rows and exits non-zero **without writing to a single
page**. It does not sweep the reviewed rows and skip the rest, and it never falls back
to the proposal. Half a sweep is worse than none: it produces a 60-file diff that looks
deliberate, and the missing banners then surface as linter errors with no indication
that a human decision was skipped rather than a page missed.

### The sweep script is a separate, throwaway deliverable

`tools/pagelint.py --fix` is **P1** in the requirements, while the banner sweep is
**P0**. The design must not make a P0 step depend on a P1 tool, so the sweep is its own
one-shot script — `spec/011-authoring_conventions/apply_banners.py` — kept beside the
spec rather than in `tools/`, because it is used once and then has no reason to exist.

The two are genuinely different jobs and should not be conflated:

| | `apply_banners.py` (P0, one-shot) | `pagelint.py --fix` (P1, durable) |
|---|---|---|
| Input | `pagetypes.tsv` verdicts | The page itself |
| Decides page type | Reads a human's decision | Never — cannot know |
| Lifetime | Deleted after the sweep | Lives with the repo |
| Job | Insert 105 banners once | Fix mechanical faults on new pages, bump the version at V11 |

Folding the TSV-reading into `--fix` would leave a durable tool carrying one-off
migration logic, and would make the V11 version bump depend on a file that by then
describes a decision made years earlier.

**Pages expected to need argument** — flagged now so review time goes where it is
needed: `FAQ.md`, `ShowMeTheCode.md` (a showcase; Reference is a poor fit but it is
not a tutorial — Spec 009 addresses the underlying problem), `WhyBrighter.md`
(Explanation), `V10MigrationGuide.md` (How-to or Reference — it is consulted, so
Reference), `Glossary.md` (Reference), and the 14 four-mode pages, whose difficulty in
choosing is itself the worklist signal.

## 2. `CLAUDE.md` Changes (D1)

Two edits in one commit. Shipping the second without the first leaves the file
contradicting itself — see requirements § This contradicts `CLAUDE.md` today.

### 2a. Amend the existing *File Organization Pattern*

Current text prescribes the skeleton with unqualified headings. The amendment keeps
the skeleton and the ordering, and adds the qualification rule:

> Follow this structure within documentation files:
>
> 1. Title (H1) — clear, descriptive
> 2. **Page banner** (see *Page Conventions*)
> 3. Introduction — brief overview (2–3 sentences)
> 4. Key Concepts, How-to/Usage, Configuration, Best Practices, Common Pitfalls,
>    Sample Code — **each heading qualified by its subject**: write
>    `## Kafka Subscription Configuration`, not `## Configuration`
> 5. Further Reading — **unqualified**, one of the five allowlisted navigation
>    headings

### 2b. New *Page Conventions* section

| Subsection | Content |
|---|---|
| Page banner | Grammar, the four page types with a sentence each on when to use them, the `Reference`-as-catch-all rule, worked examples |
| Heading qualification | The rule, the derivation (qualifier comes from the page subject), and the canonical five-item navigation allowlist quoted verbatim |
| Version markers on code | ❌ superseded / ✅ current, with an example pair |
| Complete code blocks | `using` directives, `// ...` for omissions, language tag on every fence |
| `llms.txt` | Format definition (§7 below) |
| Enforcement | What `pagelint.py` checks, repo-wide versus `--changed`, and how to run it |

**Every rule in this section maps to a linter rule, and every linter rule appears
here.** Acceptance criterion 5 is the check on that, and it is worth taking literally:
a rule in only one of the two places is how the next round of decay begins.

## 3. `tools/pagelint.py` (D4)

### Structure

Roughly 300 lines, standard library only, mirroring `linkcheck.py`'s conventions so
that someone who has read one can read the other.

```python
from linkcheck import md_files, slug, HEADING_RE   # reuse, do not duplicate

NAV_ALLOWLIST = frozenset({          # canonical; CLAUDE.md quotes this verbatim
    'Further Reading', 'Related Documentation', 'See Also',
    'Next Steps', 'References',
})
BANNER_RE = ...                      # §1
PAGE_TYPES = ('Tutorial', 'How-to', 'Reference', 'Explanation')

def check_banner(path, lines)       -> list[Finding]
def check_headings(all_pages)       -> list[Finding]   # cross-page; needs every page
def check_code_blocks(path, lines, strict_ranges) -> list[Finding]
def check_terminology(path, lines)  -> list[Finding]
def changed_ranges(merge_base)      -> dict[path, list[(start, end)]]
```

`check_headings` is the one rule that cannot run on a single file — uniqueness is a
property of the corpus. When invoked on a subset, it loads every page for context but
only *reports* on the requested ones, exactly as `linkcheck.py` handles orphans.

### Rules

| # | Rule | Repo-wide | `--changed` |
|---|---|---|---|
| 1 | Banner present as first non-blank line after H1 | error | error |
| 2 | Banner matches `BANNER_RE` (type in vocabulary, *Applies to* present) | error | error |
| 3a | `##` heading text unique **across pages**, `NAV_ALLOWLIST` exempt | error | error |
| 3b | Heading text unique **within a page**, H2–H4, `NAV_ALLOWLIST` exempt | error | error |

### Rules 3a and 3b compare `slug()`, not raw text

Both compare `slug(text)`, not the markdown as written. Four H2 texts are emphasised,
all four on the four outbox pages (`MSSQLOutbox.md`, `MySQLOutbox.md`,
`PostgresOutbox.md`, `SqliteOutbox.md`): `## **Provisioning the Outbox Table**`,
`## **NuGet Packages**`, `## **Database Table Schema**`, `## **Configuration**`. Two of
them have plain twins elsewhere in the corpus — `Configuration` ×22 and `NuGet Packages`
×5. GitBook strips the emphasis when it builds the anchor, so those pairs really do
collide in the published URL; comparing raw text would let them through. `slug()` is
imported from `linkcheck.py`, so the linter compares exactly what the link checker
resolves anchors against.

**Corrected 2026-08-04 against the linter's first run.** This paragraph previously
said normalisation moved the text count to 48 and left the instance count at 256.
Measured: normalised is **50 texts, 262 instances**, against **50 texts, 256
instances** raw. `slug()` lowercases as well as stripping emphasis, so it also merges
case variants — `## Common pitfalls` into `## Common Pitfalls`, `## NuGet packages`
into the `NuGet Packages` group, and two pairs (`How It Works`/`How it works`,
`**Configuring The Dispatcher**`/`Configuring the Dispatcher`) that were *not*
collisions raw and become collisions normalised. That last class is what the earlier
analysis missed: it accounts for +6 instances, and for the text count returning to 50
after the two emphasis merges subtracted two. The full derivation is in `tasks.md`
§ *Measured baseline*. The `NAV_ALLOWLIST` is matched
normalised too — it is declared as the five plain texts, and the linter compares
`slug()` of the heading against `slug()` of each entry, so an emphasised
`## **Further Reading**` is still exempt rather than a false positive. Rule 3b is
unaffected — 12 pages, 34 instances under either comparison.
| 4 | Fenced block carries a language tag | warning → error once P1 lands | error |
| 5 | `ServiceActivator` in prose where `Dispatcher` is meant | error | error |
| 6 | C# block carries `using` directives | **warning, counted** | **error** |

### Rule 3 is two rules, with deliberately different scopes

**3b — within a page, H2 through H4.** A heading repeated inside one page produces
`#when-to-use`, `#when-to-use-1`, `#when-to-use-2` … — anchors that no author would
choose and no reader can interpret, on chunks that sit next to each other. It is the
unattributable-chunk problem in its purest form.

Measured 2026-08-03: **12 pages, 34 duplicate instances.**

All twelve, with the repeat that fires and the number of surplus instances it
contributes. **The list is complete** — an earlier draft named ten and closed with
"+ 2 more", which left Phase 2's reconciliation unable to check the pages rather than
just the total.

| Page | Repeats | Instances |
|---|---|---|
| `InMemoryOptions.md` | `When to Use` ×5, `Configuration` ×5, `Limitations` ×3, `Example Usage` ×3 | 12 |
| `HandlerFailure.md` | `What It Does` ×4, `When to Use It` ×4 | 6 |
| `PostgreSQLMessageBroker.md` | `How It Works` ×2, `Transactional Messaging` ×2, `Configuration` ×2 | 3 |
| `ReactorAndProactor.md` | `Handlers` ×2, `Message Mappers` ×2, `Middleware/Attributes` ×2 | 3 |
| `RabbitMQConfiguration.md` | `Best Practices` ×3 | 2 |
| `Glossary.md` | `Dispatcher` ×2, `CloudEvents` ×2 | 2 |
| `AWSSQSConfiguration.md` | `AWS SDK v4 Support` ×2 | 1 |
| `BrighterSchedulerSupport.md` | `Configuration` ×2 | 1 |
| `CustomScheduler.md` | `Implementation Steps` ×2 | 1 |
| `FAQ.md` | `When should I use Reactor vs Proactor?` ×2 | 1 |
| `ImplementAQueryHandler.md` | `Complete Example` ×2 | 1 |
| `KafkaConfiguration.md` | `Configuration Callback` ×2 | 1 |
| | | **34** |

`InMemoryOptions.md` carries a fourth repeat (`Example Usage` ×3) that the earlier
table missed, so the page needs **12** qualifications rather than 10. `Glossary.md`
and `FAQ.md` appear here because of the duplicate-content pairs below — those are
**merged, not qualified**.

Bounded and one-off: 34 headings gain a qualifier at step 6, alongside the cross-page
work. Note that `RabbitMQConfiguration.md` — our own demonstrator — is on this list,
and the §6a split dissolves all three of its `### Best Practices`. That happens by
luck, not by rule; 3b is what makes it deliberate.

**3a — across pages, H2 only.** Deliberately *not* extended to H3. Measured: 39 H3
texts appear on more than one page, 112 instances — `### Basic Configuration` on 9
pages, `### Cancelling a Scheduled Job` on 6. Those are not defects. An H3 is read in
the context of the H2 above it, and `### Basic Configuration` under
`## Hangfire Scheduler Configuration` is perfectly attributable. Forcing global
uniqueness on subsection headings would generate 112 stilted renames for no gain, and
would push authors toward long, unreadable headings.

The asymmetry is the point: **within a page, a duplicate is always a defect; across
pages at H3, it usually is not.**

### Rule 5 needs care

`ServiceActivator` is legitimate in three places, and a naive ban would fire on all of
them:

- Inside fenced code blocks — `ServiceActivatorHostedService`,
  `Paramore.Brighter.ServiceActivator.Extensions.DependencyInjection`
- Inside inline code spans
- On `HowServiceActivatorWorks.md`, a page about the name itself

So the rule scans **prose outside fences and outside backticks**, and honours a
file-level opt-out comment for pages that discuss the term:

```markdown
<!-- pagelint: allow-serviceactivator -->
```

### Rule 6 and `--changed`: block granularity, not file

Deriving changed line ranges from the git merge-base, a code block is *strict* only if
it overlaps a changed range. A typo fix on a 700-line page therefore obliges nothing
beyond the typo. Requirements § D4 records the reasoning: a file-level rule makes small
corrections expensive, and the predictable result is that people stop making them.

### Output

Follows `linkcheck.py`: one line per finding, `path:line: RULE: message`, then a
summary. Exit non-zero on any error; warnings alone exit 0.

```
contents/KafkaConfiguration.md:1: BANNER MISSING: add a banner below the H1, e.g.
    > **Reference** · Applies to **Brighter V10**
contents/AwsScheduler.md:212: HEADING NOT UNIQUE: "## Best Practices" also appears in
    HangfireScheduler.md, QuartzScheduler.md. Qualify it: "## AWS Scheduler Best Practices"
contents/Telemetry.md:88: USING DIRECTIVES (warning): C# block has no `using` lines

3 errors, 41 warnings (using-directive debt: 663 blocks across 67 pages)
```

**Error messages state the fix.** Authors are the audience, and a linter that only
says "wrong" gets disabled.

## 4. `.github/workflows/docs.yml` (D5)

The repository has no CI today — verified 2026-08-03, `.github/` does not exist. This
is the first workflow, and wiring `linkcheck.py` in is part of the job.

```yaml
name: docs
on: [push, pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0            # --changed needs history for the merge-base
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: python3 tools/linkcheck.py
      - run: python3 tools/pagelint.py
      - if: github.event_name == 'pull_request'
        run: python3 tools/pagelint.py --changed origin/${{ github.base_ref }}
```

No third-party actions beyond checkout and Python setup, and no network access — both
tools are standard-library only, and keeping them that way means the build cannot fail
for reasons unrelated to the documentation.

**Land this first, running `linkcheck.py` alone**, to establish a green baseline before
any sweep. `pagelint.py` joins once the sweeps have made it pass.

## 5. Heading De-duplication (D3)

**50 heading texts, 262 instances** as the linter counts them (2026-08-04; 256 when
heading text is compared raw — see *Rules 3a and 3b compare `slug()`*). The three
allowlisted texts that appear more than
once (`Further Reading` 29, `Related Documentation` 10, `See Also` 2 — 41 instances)
stay exactly as they are.

### Deriving the qualifier

The qualifier is the page's subject, taken from its H1 with filler removed:

| Page | H1 | Heading | Becomes |
|---|---|---|---|
| `KafkaConfiguration.md` | Kafka Configuration | `## Configuration` | `## Kafka Configuration` |
| `HangfireScheduler.md` | Hangfire Scheduler | `## Best Practices` | `## Hangfire Scheduler Best Practices` |
| `MsSqlDistributedLock.md` | MSSQL Distributed Lock | `## Provisioning` | `## MSSQL Distributed Lock Provisioning` |

Where that produces something unwieldy, shorten by hand — the script proposes, a human
edits. `## Hangfire Best Practices` is better than
`## Hangfire Scheduler Best Practices` and no rule can tell you that.

### The anchor links are all same-page

Requirements flagged 8 links pointing at anchors de-duplication would rename. On
inspection **all 8 are same-page links** — no file prefix, pointing at a heading in
their own file:

| File | Link |
|---|---|
| `DynamoDbDistributedLock.md:20`, `AzureBlobDistributedLock.md:13`, `PostgresDistributedLock.md:13`, `MySqlDistributedLock.md:14`, `FirestoreDistributedLock.md:13`, `MsSqlDistributedLock.md:14`, `MongoDbDistributedLock.md:14` | `[Provisioning](#provisioning)` |
| `FAQ.md:8` | `[Configuration](#configuration)` |

So each is fixed in the same edit that renames its heading — no cross-page repointing,
and no window in which the repo is inconsistent. `linkcheck.py` catches any that are
missed.

External inbound links (blog posts, Stack Overflow) cannot be fixed from here. Eight is
small, and it will never be smaller than it is now.

Both follow the same rule: **the Reference core keeps the original file name**, so the

### 6b. `BrighterBasicConfiguration.md` (1,068 lines → 3 pages + a merge) — D7

The largest and worst-mixed page in the repo. Four H2s covering two enormous
reference dumps, a walkthrough, and a migration note.

```
BrighterBasicConfiguration.md                 How-to      ~200 lines
├── Using .NET Core Dependency Injection
├── Configuring the Command Processor — the one path that works
├── Putting It All Together (worked example, end to end)
├── Running the Dispatcher
└── A Complete Dispatcher Example
    → links out to both reference pages for every option

CommandProcessorConfigurationReference.md     Reference   ~630 lines
├── Command Processor Service Collection Extensions (lines 16–331)
├── Validating Your Configuration (332–349)
└── Brighter Builder Fluent Interface (350–648)

DispatcherConfigurationReference.md           Reference   ~210 lines
├── Dispatcher Service Collection Extensions (708–859)
└── Dispatcher Brighter Builder Fluent Interface (860–918)

V10MigrationGuide.md                          EDIT — absorbs, does not duplicate
└── V10 Configuration Changes + Quick Migration Guide (1041–1068)
```

Folding the V10 section into the existing migration guide is the "no information loss,
but no duplication either" rule in action: that content belongs with the other
migration material, and a reader looking for it will look there.

**The `## **Bold Heading**` style** used throughout this page (`## **Configuring The
Command Processor**`) is not the convention anywhere else. `linkcheck.py`'s `slug()`
strips the emphasis, so anchors are unaffected either way. Normalise it while splitting
— it costs nothing at the point the text is already being moved.

### Redirects

Both splits move content to new URLs. `.gitbook.yaml` has **no `redirects:` block**
today; adding it is Spec 010's deliverable, but if 010 has not landed when the splits
do, **the splits add it themselves** rather than shipping dead URLs.

```yaml
redirects:
  guaranteed-at-least-once/rabbitmqconfiguration: contents/RabbitMQConfiguration.md
```

No leading slashes, paths relative to `root`. **Malformed indentation disables
redirects silently rather than erroring** — verify mechanically, do not eyeball.

## 7. `llms.txt` Format (D9)

Defined here, generated by Spec 010 from `SUMMARY.md`. One line per page:

```
# Brighter and Darker Documentation

> CQRS and Messaging frameworks for .NET. Brighter handles Commands and Events;
> Darker handles Queries.

## Get Started
- [Your First Command](/contents/TutorialFirstCommand.md): Tutorial — send a command in-process, no broker required.

## Transports
- [RabbitMQ Configuration](/contents/RabbitMQConfiguration.md): Reference — connection, publication and subscription parameters.
```

Sections mirror `SUMMARY.md`. Each line is `- [Title](path): Type — one sentence.`
The type comes from the page banner, which is why the banner has to land first: the
generator reads it rather than guessing.

|---|---|
| Page | Path and line count |

| Verdict | `split` / `keep` / `keep — outside Diátaxis` |
| Proposed shape | For `split`, the target pages and which sections go where |

triage signal, not a verdict** — `Glossary.md` (589 lines, single mode) and

### Content defects surfaced by rule 3b — fix by merging, in their own commit

Rule 3b flags three duplicates that are **content defects wearing a heading defect's
clothes**, and they cannot simply be recorded for later: the rule is an error, so CI
stays red until they are resolved.

- **`Glossary.md`** defines `Dispatcher` twice and `CloudEvents` twice
- **`FAQ.md`** asks *"When should I use Reactor vs Proactor?"* twice

The temptation is to let the mechanical sweep qualify the second heading of each pair
and move on. **Do not** — that turns a visible duplicate into a permanent one and
hides it behind a heading that now looks intentional. A glossary with two entries for
one term needs the entries merged.

So these three get their **own small commit at step 6**, separate from the mechanical
qualification pass, with the merged text reviewed as a content change. Three merges is
a small enough job to absorb here; the alternative — an exemption list — would leave
the linter permanently lying about the corpus.

## 11. Style Notes

- **"Guidance" is not a page type.** The mode analysis scored it as a proxy for
  Diátaxis's ill-fitting fourth corner. Best-practice material folds into the
  explanation or how-to that owns its subject; it does not become its own page.
- **Terminology**: "Dispatcher", not "ServiceActivator", in prose — while the API
  surface genuinely uses the older name, which is why rule 5 has an opt-out.
- **Banner separator** is U+00B7, not a hyphen or pipe. Fixed so the regex can be
  strict.
- **Bold headings** (`## **Configuring...**`) are normalised only on pages already
  being edited for another reason. Not a sweep of its own.
- **The sweep commits stay mechanical.** Banner insertion and heading qualification
  are separate commits, each independently reviewable, neither carrying prose changes.
