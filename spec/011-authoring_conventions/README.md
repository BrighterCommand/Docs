# Spec 011: Page Type Discipline and Machine-Readable Conventions

**Created:** 2026-08-03
**Status:** Requirements Phase

## Topic Overview

[Docs#67](https://github.com/BrighterCommand/Docs/issues/67) observes that *"Brighter
documentation mixes different types of information."* [Spec 010](../010-information_architecture/README.md)
fixes that between pages. This spec fixes it **within** pages, and — the same change
viewed from a different angle — makes each page well-formed for machine consumption.

### The mixing problem, measured

`contents/RabbitMQConfiguration.md` (565 lines) interleaves all four Diátaxis modes:

| Section | Mode |
|---|---|
| Connection, Publication, Subscription | Reference |
| "What are Quorum Queues?", "Classic vs Quorum" | Explanation |
| "Migration from Classic to Quorum Queues" | How-to |
| "Best Practices for Connection Stability" | Guidance |

A reader who wants the subscription parameter list must read an essay on quorum queue
trade-offs to reach it. `contents/BrighterBasicConfiguration.md` does the same over
1,068 lines.

### The machine-readability problem, measured

Audit of `contents/` as of 2026-08-03:

- **0 of 110 pages** carry YAML front matter
- `## Configuration` is a heading on **22 different pages**; `## Best Practices` on
  **26**; `## Further Reading` on **29**; `## Summary` on **14**; `## Overview` on **10**
- Of roughly **1,050** C# code blocks, only about **230** include `using` directives

These matter because an LLM retrieves a *chunk*, not a page. A chunk headed
`## Configuration` is unattributable — there is no way to tell Kafka from Hangfire. A
chunk with no version marker cannot correct a model's V9-era priors, which are
plentiful: pre-V10 Brighter is well represented in blog posts and Stack Overflow
answers, and a model with no counter-evidence in context will confidently emit
configuration that no longer compiles. A snippet missing its `using` directives gets
hallucination-completed with plausible but wrong namespaces.

Every one of these fixes also helps a human: subject-qualified headings improve search
results and page scanning; version markers stop readers pasting V9 code; complete
snippets compile when pasted.

## Proposed Conventions

**1. A visible page banner on every page.**

The original plan was YAML front matter. **That is ruled out** — see the platform
finding below. Instead each page opens with a one-line banner, immediately after the
H1:

```markdown
# RabbitMQ Subscription Configuration

> **Reference** · Applies to **Brighter V10** · Prerequisites: [Basic Configuration](/contents/BrighterBasicConfiguration.md)
```

This turns out to be the better design for both audiences, not merely the available
one:

- It **renders** — a reader sees the page type and version without viewing source,
  which front matter never gave them
- It **survives chunking** — retrievers routinely strip front matter before embedding,
  whereas body text stays attached to the chunk that needs it
- It is **regex-parseable**, so the linter can still enforce it mechanically

The structured form of the same metadata lives in `llms.txt`, generated by Spec 010.

**2. Subject-qualified headings.** `## Configuration` becomes `## Kafka Subscription
Configuration`. Zero cost, removes ambiguity for retrieval and for search.

**3. Version markers on code.** Where V9 and V10 differ, show both, labelled — ❌ for
the superseded form, ✅ for current. Putting the discrimination in the text is far
more reliable than trusting the reader (or the model) to already know.

**4. Complete code blocks.** `using` directives present; `// ...` marking genuine
omissions. `CLAUDE.md` already requires this; the 230-of-1,050 ratio says we do not
comply.

**5. `llms.txt`** at repo root — the emerging convention for a curated, one-line-per-page
index that an agent fetches to find the canonical page for a topic. Generated from
`SUMMARY.md`; the generator ships with Spec 010, the convention is defined here.

**6. Tool enforcement.** Extend `tools/linkcheck.py`, or add a sibling linter, to
check: front matter present and valid; no duplicate `##` headings across pages;
banned terminology (`ServiceActivator` where `Dispatcher` is meant). Conventions that
are not machine-checked decay.

## Platform Finding: No Front Matter (resolved 2026-08-03)

Investigated via GitBook's own documentation rather than assumption. GitBook's docs
state plainly that front matter is not the supported route:

> *"If you were hoping to control page behavior using YAML front matter, the docs route
> that you can rely on is `.gitbook.yaml`, not front matter in the Markdown itself."*

Front matter is undocumented for Git Sync, no key set is specified, and
[GitbookIO/gitbook#1079](https://github.com/GitbookIO/gitbook/issues/1079) reports that
front matter added to a page renders literally into the output. Shipping it across 110
pages risked a block of raw YAML at the top of every published page.

**Decision:** use the visible banner convention above. No trial branch needed; the
platform answer is clear enough that the experiment is not worth the review cycle.

Confirmed in the same investigation, for Spec 010's benefit: `.gitbook.yaml` **does**
support a `redirects:` block, mapping old path to new file, with no leading slashes and
paths relative to `root`.

## Scope

- Add the conventions section to `CLAUDE.md`
- Add the page banner to all pages under `contents/`
- Split the worst mixed-mode offenders — `RabbitMQConfiguration.md` and
  `BrighterBasicConfiguration.md` at minimum; select the rest by size and mode-mixing
- De-duplicate generic headings
- Build the linter and wire it into CI alongside `linkcheck.py`

## Out of Scope

- Rewriting prose for style. This is structural.
- Backfilling `using` directives across all 1,050 code blocks in one pass — define the
  rule and enforce it for new and touched pages; sweep the rest incrementally.

## Open Questions

Both resolved 2026-08-03 — see `requirements.md` § Resolved Questions.

1. ~~How aggressively do we split?~~ **Not by size, and mostly not here.** Size is the
   wrong criterion: `Glossary.md` (589 lines) and `KafkaConfiguration.md` (606) are
   single-mode and should not be split, while `ReactorAndProactor.md` (440) mixes all
   four. Candidates are scored by mode mixing, and **this spec ships only the two
   demonstrator splits** — `RabbitMQConfiguration.md` and `BrighterBasicConfiguration.md`
   — handing a scored worklist to Spec 010, which executes the rest while re-filing.
   See the scope note below.
2. ~~Banner above or below the H1?~~ **Below.** Keeps the H1 first for GitBook's title
   extraction, and the measurement makes it unambiguous: 0 of 107 pages currently open
   with a blockquote after the H1, so "first non-blank line after the H1" is a rule the
   linter can enforce with no legacy exceptions.

## Scope Change Since This README (2026-08-03)

Splitting moved from this spec to Spec 010. Splitting a page creates new pages needing
names, `SUMMARY.md` placement and redirects — all of which 010 owns and is already
doing to the same files. Doing it here would touch the split pages twice and produce
two overlapping diffs, which is exactly what the 011-before-010 ordering was chosen to
avoid. This spec keeps the rule, the linter and two demonstrators.

## Execution Order

Spec numbers are identifiers, not a sequence. This spec runs **first** of the
restructuring group: **011 → 010 → 012 → 013**, with Spec 009 in parallel throughout.
Running 011 before 010 avoids editing all 110 pages twice — once to add banners, once
to move them — and avoids two large overlapping diffs over the same files.
